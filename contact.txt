**5) 【严重·可用性】一次 `/c/` 请求就把整个服务器打崩（SIGSEGV）**
- `libs/app-engines/samples/c-plugin/plugin.c` **没有 include `<stdlib.h>`**，
  `getenv` 按隐式 `int getenv()` 编译 → 64 位指针被截成 32 位再解引用：
  ```
  237d: movslq %eax,%rcx      ; getenv 的返回值被截断
  2380: cmpb   $0x0,(%rcx)    ; SIGSEGV
  ```
  触发条件：`www-apps/c/.env` 里有 `APP_HELLO=c`，host 通过 extra JSON `setenv` 注入后
  `getenv` 返回非 NULL → 必崩。32 位截断只是隐患，指针一非空就是确定性的崩溃。
  **这是远程 DoS：任何能访问 /c/ 的人都能让整个 Web 服务器退出。**
  之前没暴露是因为 `port_reuse` 让 /c/ 只返回 301，C 引擎从未被真正执行过
  （上面第 3 条修好后第一次真跑就崩了）。
  已加 `#include <stdlib.h>`；并在 `build_app_engines.sh` 的 CFLAGS 加
  **`-Werror=implicit-function-declaration`**，让这类隐式声明在编译期就失败。
  实测修复后：`/c/` 返回 200 且 body 为 `c path=/c/`（APP_HELLO 注入生效），
  15 个引擎全部有响应、服务器存活、TLS/h3 正常。

**改动（都已上线）**
```

src/server/apps/env_lock.rs    空 .env 时不再拿按引擎的锁（5bab654 → build32）
```

**① 关停截止时间（build31）**：`rt.shutdown_timeout(3s)` + 8s 看门狗 `exit(exit_code)`。
**诚实说明**：那次「进程带一个连接残留 6 小时」的根因**没能复现**（我用「CGI 有卡住请求在场」
构造场景，新旧二进制都 0~1s 退出，等于证伪了我原来的猜测）。所以这条是**兜底加固**：
把"可能永不退出"变成"8s 内一定退出"。另一个更可能的解释：早先某次 stop 的 `pkill`
把自己的 ssh 会话先杀了，那个进程**根本没收到信号**（本轮我又踩了一次同样的坑，见下）。

**② env_lock 串行化（build32，本轮最有价值的修复）**：验证关停时顺手做的并发实验发现
一个 `sleep 120` 的 CGI 会让 `/cgi/` **整条路径排队超时**。根因：非内联引擎的调用被包在
`env_lock::with_temp_env_named` 里，它**无条件**取「按引擎」的锁并**持有整个引擎调用期**；
而 `.env` 为空（默认）时什么都不用设却照样拿锁 → 同一引擎的所有请求退化成串行。
修法：`vars.is_empty()` 直接 `return f()`。
**A/B 证据**（同一脚本）：修前 `/cgi/` 在慢脚本在场时 6s 超时；修后 **200 / 7ms**，
且同时有 4 个 `sleep` 子进程并存在跑。影响面是所有非内联引擎（php/lua/python/cgi/…）。
遗留：`.env` 非空时该引擎仍串行（进程级 env 互斥是硬约束），彻底解决要走 ABI 的 extra JSON。

**③ 又踩的坑（这次是"停/起同一条命令"的新变体）**：把 kill 和 start 写在同一条远程命令里时，
**start 那段的字面量（如 `config-test.toml`）会被前面的 pkill 匹配到**，于是先杀掉自己的 shell，
后面的启动根本没执行（我因此以为停了测试实例，其实它还在跑）。必须分成两次独立调用。

**④ 顺带**：只改本 crate 的代码时远程构建只要 **7~8 分钟**（依赖已缓存）；动到依赖才 21~24 分钟。

## 我另外修的：**J 项**「h1/h2 已建立连接沿用建连时的 listener 策略」
这是 J 项里唯一还没修、且有**安全含义**的一条：h1/h2 在 accept 时拿走一份 `ListenerConfig`，整条连接
的所有请求都用它 ⇒ `root`/`basic_auth`/`page_rules`/`file_open`/限流 改了之后，**已建立**的连接
永远沿用旧策略（只有新连接拿到新配置）。**改 `basic_auth` 的口令「改了没生效」**就是这个后果。
修法（最小、不动请求语义）：`LiveConfig` 加一个**只在 listener 配置指纹真的变了**才推进的代数
（复用 `h3_config_fingerprint`，含证书 mtime）；h1 在响应上写 `Connection: close`，h2 发一次 GOAWAY
（**不发就断开**：h2 一条连接上可能有几十个在飞请求，直接 drop `conn` 会全部打断）。
只按指纹推进是关键 —— 否则改一条 `[access_log]`、甚至保存一次内容相同的文件，就会把所有在线连接
赶下线。

**判据是六条，前三条是反向判据**（防「修过头」）：h1 不改配置→不得 close、只改 `[access_log]`→不得
close、改 root→必须 close 且**新**连接拿到新 root；h2 同构的两条 + 「必须 GOAWAY」。
**先在未修的二进制上跑了一遍作为负控**：三条反向判据全 PASS、两条正向判据全 **FAIL**
（旧连接照旧服务旧 root、不发 GOAWAY），而**新**连接能拿到新 root ⇒ 精确地把「只是已建立连接过期」
这一条隔离出来了。脚本固化在 `scripts/verify/listener_staleness.{sh,_h1.py,_h2.js}`
（h2 用 node 自带 http2 模块：curl 看不到 GOAWAY 帧）。

统一口径：**细节只进本地日志，客户端拿固定文本**。
